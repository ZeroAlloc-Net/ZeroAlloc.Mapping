# Mapping v1.4 — decisions log

Working notes captured during brainstorming. Each entry records what was
locked AND what was considered-and-rejected, with reasoning. When the
brainstorm completes this rolls up into the canonical design doc.

Date opened: 2026-05-23
Bundle: v1.4 graduates B3 (IQueryable projections), B6 (cycle detection),
B11 (UseDeepCloning) from `docs/backlog.md`. B7 (private member mapping)
was discussed and explicitly dropped — see policy entry below.

---

## Policy override

The four open items in `docs/backlog.md` are all marked "deferred until
consumer signal fires." Shipping any of them now is technically against

The override applies ONLY to graduation timing, NOT to the

## D-1: B7 dropped from bundle

**Locked:** B7 (private member mapping) does NOT ship in v1.4. Remains
in `docs/backlog.md` as the deliberate policy statement.

**Rationale:** B7 is fundamentally different from B3/B6/B11. The latter
three are *deferred-pending-signal*; B7 is *explicitly out-of-scope by
design*: "Encapsulation-breaking by design. Documented as
out-of-scope-by-design." Shipping it reverses a philosophical stance,
not just an ordering decision.

**Considered:**
- **B7-fully-open** (`IncludePrivate = true` flag emitting reflection
  to reach truly private members): rejected. Crosses two clear lines
  the package guards — encapsulation AND zero-alloc-no-reflection.
- **B7-strict** (only map members the generator can already see —
  internal-in-same-assembly or `InternalsVisibleTo` cases): defensible
  but the user chose to drop B7 entirely rather than partially relax.
  Keeps the public policy statement intact.

## D-2: B3 — surface for `IQueryable` projection

**Locked:** Opt-in via `[Map<TSrc, TDst>(Projection = true)]`.
When `true`, the generator additionally emits
`public static Expression<Func<TSrc, TDst>> Projection { get; }` on the
declaring class, alongside the existing static `Map` method.

Consumer usage:
```csharp
db.Orders.Select(OrderMapper.Projection).ToList();
```

**Rationale:**
- The package's static-mapper-class pattern doesn't fit the
  `IQueryable<T>.ProjectTo<TDst>()` extension shape that AutoMapper
  / Mapster use; a static property is the natural fit.
- Opt-in respects the original deferral reasoning: B3 was deferred
  because `ZeroAlloc.Specification` already covers expression-tree
  construction. Keeping it opt-in says "EF projection is a separate
  surface area, not a default."

**Considered:**
- **B3-always-on** (every `[Map<,>]` automatically emits a `Projection`
  property): rejected. Pulls `System.Linq.Expressions` into every
  generated mapper and pays a one-time static-init cost building the
  expression tree even for DTOs that will never be projected. Most
  vertical-slice DTO mappings have no EF Core consumer.
- **B3-separate-attribute** (`[MapProjection<TSrc, TDst>]` decoupled
  from `[Map<,>]`): rejected. Over-engineered — DTOs that need
  projection almost always also need a runtime `Map` for non-EF
  callers, so a single attribute with a `Projection` knob carries
  fewer moving parts.

## D-3: B3 — feature subset that survives projection

**Locked:** Hard compile-time error `ZAMP017` when `[Map(Projection = true)]`
is used on a mapping that ALSO uses any of:
- `[MappingHook]` methods (B4)
- `[MappingCulture]` parsing (B9)
- Polymorphic dispatch via `[PolymorphicMap]` (B2)

The user must either remove the incompatible feature or remove
`Projection = true`. Generator refuses to emit.

**Rationale:** The projection contract must mean the same thing as the
runtime mapper. EF Core's LINQ translator can't handle user method
calls, `IFormatProvider` lookups, or (in general) runtime type
switching. Fail-fast at compile time is consistent with how v1.3
already handles "you can't combine X and Y" cases (e.g. ZAMP016 for
duplicate `[MappingCulture]`).

**Considered:**
- **Warning + silently strip in projection emit:** rejected. The
  runtime `Map` and the projection would semantically diverge — same
  attribute, different behaviour depending on call site. Dangerous.
- **No diagnostic; emit a projection that calls into the runtime
  mapper** (`src => OrderMapper.Map(src)`): rejected. Defers the
  failure to EF Core's runtime translator. Worse user experience than
  a compile-time error.

## D-4: B3 — nested mappings inline silently

**Locked:** When `[Map<Order, OrderDto>(Projection = true)]` references a
nested type with its own `[Map<NestedSrc, NestedDst>]`, the generator
inlines the nested mapping's body into the outer `Projection`
expression tree. The nested mapping does NOT need its own
`Projection = true` declaration.

Emit shape:
```csharp
src => new OrderDto {
    Customer = new CustomerDto { Name = src.Customer.Name, ... },
    ...
}
```

**Rationale:** EF Core can't translate cross-mapper calls
(`CustomerMapper.Map(src.Customer)` kills SQL generation). The
generator already collects the nested mapping's member structure for
the runtime emit; reusing it for the projection inline costs nothing
extra. Auto-inline keeps the user's attribute footprint minimal.

The ZAMP017 fail-fast from D-3 propagates transitively: if a nested
mapping uses hooks/culture/polymorphic, the OUTER mapping with
`Projection = true` fires ZAMP017 because the inlined emit would have
to drop the incompatible features.

**Considered:**
- **Explicit opt-in chain** (`Projection = true` required on every
  transitive mapping; new diagnostic ZAMP018 if missing): rejected.
  Burdens the user with attribute bookkeeping for an emit-time detail
  they can't observe.

## D-5: B3 — Projection applies to forward direction only

**Locked:** `[Map<TSrc, TDst>(Projection = true)]` emits a `Projection`
property going `TSrc → TDst`. If the user also declares `[ReverseMap]`,
the reverse `[Map<TDst, TSrc>]` does NOT automatically get a
`Projection` — the user must explicitly declare
`[Map<TDst, TSrc>(Projection = true)]` to get reverse-direction
projection.

**Rationale:** EF Core projection is overwhelmingly used in the
entity → DTO direction. Mirror-projecting from DTO back to the entity
is a niche case where the user can opt in explicitly. Keeps the
attribute semantics one-to-one: one `Projection = true` declaration,
one emitted `Projection` property.

## D-6: B6 — cycle handling, detect-and-handle (dict cache)

**Locked:** When `[Map<TSrc, TDst>(CycleSafe = true)]` is set, the
generator emits a cycle-safe mapping that caches already-built
destinations in a `Dictionary<object, object>` keyed by reference
equality. On revisit, the cached destination is returned — back-refs
in the source graph resolve to the same destination instance in the
output graph.

**Rationale:** The graduation signal explicitly named "ORM-heavy
aggregate with parent/child back-refs" — that's the dict-cache case,
not a throw-on-cycle case. Building a real graph (not just detecting
the cycle) is what real consumers need.

**Considered:**
- **Detect-and-throw** (`HashSet<object>` tracker, throws on revisit):
  rejected. Same protection can be achieved by NOT opting in and
  letting cycles stack-overflow loudly. Detect-only adds machinery
  without solving the "I have a real graph" problem.
- **Switchable enum** (`CycleHandling.Throw` vs `CycleHandling.Cache`):
  rejected. Doubles the surface area without clear daylight.

## D-7: B6 — opt-in granularity, transitive enforcement

**Locked:** `[Map<TSrc, TDst>(CycleSafe = true)]` is per-mapping
opt-in. The generator emits two overloads on the declaring class:
- `public static TDst Map(TSrc src)` — entry point. Allocates a fresh
  `Dictionary<object, object>(ReferenceEqualityComparer.Instance)`
  and forwards to the tracker-accepting overload.
- `internal static TDst Map(TSrc src, IDictionary<object, object> tracker)` —
  recursive helper. Checks cache, registers the new destination
  BEFORE walking children (handles self-cycle), walks children.

Every nested mapping reachable from a `CycleSafe = true` mapping must
ALSO declare `CycleSafe = true`. New diagnostic **ZAMP018** fires
when a CycleSafe mapping references a non-CycleSafe nested mapping.
User must annotate the whole transitive graph explicitly.

**Rationale:** Explicit-over-magic. The user can look at a single
`[Map<,>]` declaration and tell whether it participates in cycle-safe
mapping. Auto-propagation (mirror of B3's D-4) was considered but
rejected: cycle handling is a runtime semantic, not just an emit
shape — propagating it silently behind the user's back creates
non-local reasoning ("why did this mapping get a second overload?").
For projection (D-4) auto-inline is fine because it's purely
emit-time and doesn't change runtime behaviour; for cycle handling,
explicit opt-in is worth the bookkeeping cost.

**Considered:**
- **Silent degradation** (CycleSafe mapping silently calls
  non-CycleSafe nested mapping via its normal `Map(src)`): rejected.
  User thinks they have cycle protection, then stack-overflows when
  a transitive type cycles. Loud is better than silent.
- **Auto-propagation closure** (declare once, generator computes the
  transitive closure and emits the tracker-accepting overload on every
  reachable mapper): rejected. Behavior is non-local and surprising
  — a Customer mapping that didn't ask for CycleSafe gets an extra
  internal overload because some unrelated Order chain happens to
  reach it.

## D-8: B11 — DeepClone scope and audit

**Locked:** `[Map<TSrc, TDst>(DeepClone = true)]` causes the generator
to emit a per-property deep copy for any complex-typed property
(including collections, nested objects) where no explicit nested
`[Map<,>]` declaration exists. Explicit `[Map<,>]` declarations
always win — they remain the family idiom.

For a property `List<Tag> Tags` (no explicit `[Map<Tag, TagDto>]`):
```csharp
dst.Tags = new List<Tag>(src.Tags.Count);
foreach (var __item in src.Tags)
    dst.Tags.Add(new Tag { Name = __item.Name, Id = __item.Id, ... });
```

For a property `Customer Customer` (no explicit
`[Map<Customer, CustomerDto>]`):
```csharp
dst.Customer = new Customer { Name = src.Customer.Name, ... };
```

**Cloneability audit:** new diagnostic **ZAMP019** fires when a
reachable type can't be cloned (no public parameterless ctor, no
settable members, or all members are init-only and not in a primary
constructor). No silent shallow fallback. Solves the
"deep-cloning makes generated code hard to audit" objection from the
backlog by failing loudly at compile time when the user asked for
something the generator can't deliver.

**Rationale:**
- Honest semantics: "deep" should mean "deep" — collections AND
  nested objects.
- Auditable: every cloned field is a literal property assignment the
  user can read in the generated source. No reflection, no
  hidden behaviour.
- Zero-alloc-during-Map preserved at the SAME boundary as before:
  the user opted into the extra allocation by asking for DeepClone.
  Allocations that happen are explicit and visible in the emit.

**Considered:**
- **Collections-only deep clone:** rejected. Leaves the more
  dangerous case (shared mutable nested object) untreated. A user
  who asks for "deep" expects deep.
- **Silent shallow fallback** for un-cloneable types: rejected.
  Same "silent degradation" anti-pattern we rejected in D-7. Audit
  difficulty was the deferral reason — solving it means failing
  loudly.

## D-9: B11 — DeepClone depth + type-graph cycle handling

**Locked, depth:** Deep-clone recursion is FULLY transitive. The
generator walks the reachable-type graph at compile time and emits
the full clone tree as literal C#. Order → Customer → Address gets
all three types cloned. Value-typed properties (primitives, structs)
are bit-copied via standard assignment; the recursion only descends
into reference types.

**Locked, cycles:** Type-graph cycles (Order → Customer → Order
back-ref) require the user to compose `DeepClone = true` with
`CycleSafe = true`. New diagnostic **ZAMP020** fires at compile
time when the generator detects a cycle in a `DeepClone = true`
type graph WITHOUT a matching `CycleSafe = true`. The user fixes
it by adding `CycleSafe = true` (and on the transitive closure per
D-7) OR by adding an explicit nested `[Map<,>]` at the cycle
boundary to break the recursion.

When both `DeepClone = true` AND `CycleSafe = true` are set on a
mapping with a cyclic type graph, the deep-clone emit threads the
runtime tracker through every nested clone — the cycle resolves at
runtime via the cache.

**Deferred (implementation reality).** The routing fork in
`MapEmitter` currently picks **CycleSafe first** when both flags are
set — `EmitCycleSafeMapPair` runs and `DeepCloneEmitter` does NOT.
Reference-typed properties on the cycle-safe path are walked via the
standard nested-mapping lookup; properties WITHOUT an explicit nested
`[Map<,>]` fall through to the standard conversion path (alias, not
literal clone). ZAMP019 is suppressed under `CycleSafe = true` to
match (symmetric with the existing ZAMP020 suppression for cycles).
ZAMP018's transitive CycleSafe enforcement catches missing nested
declarations, so users wanting deep semantics across a cyclic graph
today must declare an explicit nested `[Map<,>]` for every
reachable type. Full integration of deep-clone literal walks WITH
tracker threading is tracked as `docs/backlog.md` item B12.

**Rationale:**
- Recursive-deep is the only consistent interpretation of "deep."
  One-level depth is a half-measure that contradicts the naming.
- Composing DeepClone + CycleSafe is exactly the case the two
  features were designed to address together. Diagnosing the
  combination via ZAMP020 makes the requirement explicit at the
  declaration site.

**Considered:**
- **Auto-promote** (cyclic type graph + DeepClone silently turns
  on cycle-safe emit too): rejected. Same "silent runtime behaviour
  change" we rejected in D-7. Magic.
- **Hard error, no fix path** (cycles + DeepClone = error, full
  stop, user must break the cycle with an explicit nested `[Map<,>]`):
  rejected. Too restrictive — the user has legitimately said "deep
  clone with cycle handling" and the generator should support that
  combination explicitly.

## D-10: cross-feature compatibility matrix

**Locked:** All pairwise combinations of Projection, CycleSafe, and
DeepClone are valid. No additional diagnostic fires for combinations
beyond ZAMP017, ZAMP018, ZAMP019, ZAMP020 already specified.

Reasoning per pair:

- **Projection + CycleSafe.** Compatible. Projection emits a static
  `Expression`; CycleSafe emits an additional `Map(src, tracker)`
  overload. The two are independent. Runtime callers using
  `OrderMapper.Map(src)` get the cycle-safe path; EF callers using
  `OrderMapper.Projection` get an Expression that EF translates to
  SQL (which has no cycle concept at the SQL level).

- **Projection + DeepClone.** Compatible. Projection's emit is
  already deep-clone-by-construction (every property assigned
  explicitly in `new TDst { ... }`). DeepClone on the same mapping
  also affects the runtime `Map` body; Projection is unaffected.
  The combination is redundant on the projection side but useful
  if the runtime caller also wants deep semantics.

- **CycleSafe + DeepClone.** Routing-fork: CycleSafe wins; the
  DeepClone literal walk does NOT activate. `EmitCycleSafeMapPair`
  runs, ZAMP019 is suppressed (symmetric with ZAMP020). Users must
  declare an explicit nested `[Map<,>]` for each reference-typed
  property requiring deep-clone — CycleSafe's ZAMP018 transitive
  enforcement guarantees full coverage. ZAMP020 still directs users
  toward `CycleSafe = true` when a deep-clone walk hits a cyclic
  type graph, but the deep-clone semantic across the cycle is
  achieved via explicit nested declarations, not via the
  DeepCloneEmitter walker. Full integration is deferred — see
  `docs/backlog.md` B12.
